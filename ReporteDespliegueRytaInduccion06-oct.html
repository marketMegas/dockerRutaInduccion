1. Resumen ejecutivo

Durante el 06-oct-2026 se desplegó en el VPS el stack nuevo de la Ruta de Inducción, correspondiente a la rama segundaSimple del repositorio github.com/marketMegas/dockerRutaInduccion. El stack nuevo reemplaza a nivel de dominio la funcionalidad del sitio /rutainduccion/ (SPA React + API Django con administración) sin tocar el stack antiguo (/rutadeexpertos/, que sigue activo).

Decisión de arquitectura tomada en el día

  • Servir mobiliario nuevo y viejo en paralelo desde el mismo VPS y el mismo dominio, conmutado por prefijo de URL.
  • Los puertos de los contenedores nuevos se publicaron solo en loopback (127.0.0.1); el TLS lo termina OpenLiteSpeed (443) y el redirect http→https lo hace nginx (80). Nunca exponer 5137/5138/8000/8001 al exterior.
  • Base de datos restaurada desde el backup db.sqlite3.bak-antes-borrar-autoglp (la más completa).
  • El mecanismo efectivo de ruteo/proxy en este servidor resultó ser el bloque rewrite con [P] del .htaccess (no los context proxy de LiteSpeed; ver sección 6.F y 11).

4.1 Puntos clave del modelo

  • Puerto 80: solo nginx del sistema; redirige todo a https (301 al dominio canónico). El listener :80 de LiteSpeed quedó inactivo (nginx se quedó con el bind).
  • Puerto 443: OpenLiteSpeed con dos vhosts (www.megas.com.co y megas.com.co) que comparten el mismo docRoot (/home/www.megas.com.co/public_html).
  • El ruteo efectivo son los rewrites [P] del .htaccess (auto-cargado, sin reinicio de LiteSpeed). Los context proxy declarados en los vhost.conf (se añadieron en el día, ver 6.F) no dispararon en esta instalación; por eso la solución real quedó en el .htaccess.
  • El .htaccess es compartido por ambos vhost (mismo public_html); al ser autoLoadHtaccess 1 y leerse en vivo, los cambios se aplican sin reiniciar LiteSpeed.
  • Los contenedores nuevos NO se exponen: LiteSpeed/nginx del host los alcanzan por 127.0.0.1. Los contenedores viejos (rutadeexpertos) sí publican en 0.0.0.0, pero el firewall solo deja pasar 80/443.
  • X-Forwarded-Proto: el proxy de LiteSpeed envía X-Forwarded-Proto: https y X-Forwarded-Host al backend (verificado con sonda). Django lo honra con SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO','https'), así los correos y certificados generan URLs https.
El contenedor frontend tiene su PROPIO nginx.conf (archivo nginx.conf en la raíz del repo) que, además de servir la SPA, vuelve a proxear /api/, /admin/ y /static/ hacia backend:8000 por la red interna. Es el "plan B": si algún día LiteSpeed apunta el frontend delante de todo, el proxy interno sigue funcionando. Actualmente la entrada es LiteSpeed → .htaccess [P] → cada contenedor.

Fase F — Routing externo (la parte más delicada)

  1. Estado previo: /api/ se resolvía por una regla rota (backend_api apuntando a un extprocessor inexistente, 500), y el frontend viejo tomaba /admin/ y /static/ por un contexto anidado defectuoso (404).
  2. Primer intento: editar /usr/local/lsws/conf/vhosts/www.megas.com.co/vhost.conf agregando context /api/, context /admin/ y context /static/ de tipo proxy con handler dockerBackend_Induccion + lswsctrl restart. Resultado: 404 (LiteSpeed no honró los contexts).
  3. Segundo intento: replicar los mismos contexts en el segundo vhost (megas.com.co/vhost.conf). Resultado: 404 igual.
  4. Diagnóstico con el cuerpo de las respuestas: /admin/login/ devolvía la página de login de Django y /api/foro/temas/ el JSON real del backend NUEVO en cuanto se toparon. El 404 era cuestión de cuándo se aplicaba la config: los cambios en .htaccess se leen en vivo.
  5. Solución efectiva: rewrites proxy [P] en /home/www.megas.com.co/public_html/.htaccess apuntando a los extprocessors por nombre (mismo mecanismo que ya usaba /rutainduccion y /rutadeexpertos): 
    # 4. Backend nuevo de la Ruta de Induccion: API, admin y estaticos
RewriteRule ^/?api/(.*)$    http://dockerBackend_Induccion/api/$1   [P,L]
RewriteRule ^/?admin/(.*)$  http://dockerBackend_Induccion/admin/$1 [P,L]
RewriteRule ^/?static/(.*)$ http://dockerBackend_Induccion/static/$1 [P,L]
    Al ser autoLoadHtaccess 1, se aplica en vivo sin reiniciar. Resultado: todas 200.
  6. Aclaración arquitectónica: en esta instalación los contexts proxy de LiteSpeed no maduran; la vía fiable (y ya usada previamente) son los rewrites [P] con la dirección http://<nombre_extprocessor>/..., donde el host del rewrite coincide con el nombre de un extprocessor declarado a nivel de servidor en httpd_config.conf.
  7. Se limpió el .htaccess de reglas muertas: backend_api, regla antigua /api/ y /api-induccion. Backup .htaccess.pre-deploy.*.
  8. nginx del host (puerto 80): se reemplazó el server block por defecto por un redirect total a https (return 301 https://www.megas.com.co$request_uri), preservando /.well-known/acme-challenge/ hacia /usr/local/lsws/Example/html (webroot compartido con litespeed para renovación de certificados). nginx -t OK + systemctl reload nginx.
  9. Verificación "sonda": se escribió un mini servidor HTTP en 127.0.0.1:8100, un extprocessor probe temporal y una regla rewrite temporal para inspeccionar las cabeceras que LiteSpeed envía al backend a través del rewrite [P]. El log mostró:
PATH=/probex/zz/aa
host: www.megas.com.co
X-Forwarded-Host: www.megas.com.co
X-Forwarded-Proto: https
X-Forwarded-For: 177.7.49.5

→ Confirma que el backend recibe https en X-Forwarded-Proto; con el SECURE_PROXY_SSL_HEADER de Django las URLs absolutas (correos, certificados, CSRF) se generan como https. La sonda se retiró al terminar (extprocessor y regla eliminados, proceso cerrado, archivos temporales borrados).

11. Hallazgos del entorno y trampas conocidas

  • LiteSpeed no aplica context proxy en esta instalación (probado en ambos vhosts). El ruteo por proxy efectivo son los rewrites [P] con host = nombre de extprocessor. Los contexts añadidos hoy quedaron colocados en los vhost.conf (inactivos) — limpieza estética opcional.
  • vhost doble: www.megas.com.co y megas.com.co comparten docRoot; por eso el .htaccess es válido para ambos. En el vhost megas.com.co, los contexts /api-//admin//static quedaron anidados dentro del bloque del context acme-challenge (defecto estético; sin impacto porque el ruteo real está en el .htaccess). No intentar "arreglarlo" sin saber que los contexts no son el mecanismo vivo.
  • IPtables / firewalld: tras systemctl restart docker (o un reinicio) a veces faltan las cadenas DOCKER-FORWARD y los puertos dejan de publicarse. Remedio: reiniciar docker otra vez y docker start los contenedores restart=no.
  • DNS en builds: pip/npm dentro de docker build falló; usar --network host.
  • Compose "v5.1.3": binario no estándar pero funcional; acepta --env-file. No confiar en etiquetas por defecto.
  • :latest es engañoso: es la imagen de otro intento. Etiquetar SIEMPRE por APP_VERSION.
  • Emails duplicados en auth_user (3× marketingmagas2026@gmail.com): inofensivos por el filter().order_by('id').first().
  • El nginx.conf de la raíz del repo es el del CONTENEDOR frontend (COPY nginx.conf /etc/nginx/conf.d/default.conf). Ojo: existe también frontend/nginx.conf (legacy) y filesParaDeploy/nginx-host.conf (borrador de host).
  • El tag 8de9757 del backend es el comit del build correcto del backend (el código del backend no cambió en 7da92ae, ese commit solo tocó el frontend).
  • Env del frontend corre a través de litespeed: el proxy de litespeed manda X-Forwarded-Proto/Host/For; el nginx interno del contenedor los reenvía sin pisarlos (usa $http_x_forwarded_proto con fallback $scheme).
  • Puerto 80 lo tiene nginx (no liteSpeed); ss -lntp lo confirma: nginx 0.0.0.0:80, litespeed :443. No intentar "arreglar" el listener 80 de liteSpeed.

# El TLS lo termina el nginx del host... se reenvia X-Forwarded-Proto.
map $http_x_forwarded_proto $forwarded_proto {

    ''      $scheme;

    listen 80;
    server_name localhost megas.com.co www.megas.com.co;
    root /usr/share/nginx/html;
    absolute_redirect off;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $forwarded_proto;
    client_max_body_size 20M;

    location = / { return 302 /rutainduccion/; }
    location = /rutadeexpertos { return 301 /rutainduccion/; }

    location /admin/   { proxy_pass http://backend:8000; }
    location /static/  { proxy_pass http://backend:8000; }
